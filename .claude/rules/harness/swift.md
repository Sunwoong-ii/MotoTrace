# Swift

## 먼저 확인

- 수정할 타겟의 Swift 버전, language mode, 최소 배포 타겟을 확인한다.
- 포매터·린터 설정(SwiftLint, swift-format 등)이 있으면 그 규칙을 우선한다.
- 네이밍, 파일 구성, 접근 제어, extension 분리 방식은 주변 코드를 따른다.

## 작성

- 값 타입(struct, enum)을 우선한다. 상속 의도가 없는 class는 `final`로 선언한다.
- 접근 제어는 필요한 최소 범위로 둔다. 모듈 밖에서 쓰는 API만 `public`으로 연다.
- `!`, `try!`, `as!`를 쓰지 않는다. 불변식이 보장되는 경우만 예외로 하고, 이유를 주석으로 남긴다.
- 에러를 조용히 삼키지 않는다. `try?`로 버리는 것이 의도라면 이유를 남긴다.
- 최소 배포 타겟보다 새로운 API는 `@available` / `#available`로 감싼다. deprecated API는 새로 쓰지 않는다.
- 확실하지 않은 API는 추측해서 쓰지 않는다. SDK나 문서로 시그니처를 확인한다.
- `print` 디버그 출력, 쓰지 않는 코드·import를 남기지 않는다. 로그는 프로젝트의 로거를 쓰고, 없으면 `os.Logger`를 쓴다.
- 주석은 "왜"만 설명한다. 코드가 이미 말하는 내용은 적지 않는다. 주석 언어는 프로젝트를 따른다.
